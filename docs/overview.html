1. Project description

CoreSat is a personal portfolio management app built around the Core-Satellite strategy: a low-cost passive ETF core (~80%) plus a small set of active stock picks (~20%).

The user journey:

  1. Guided wizard — set initial capital & monthly contribution → pick the Core ETF from a fund database (compare TER, CAGR, fund size, region mix side by side) → pick Satellite stocks and weights → review & save.
  2. Main dashboard — allocation pie, current situation, growth projection to 10/20 years (CAGR-based, net of TER, with ±1% sensitivity band), and a portfolio-health radar over six criteria.
  3. Core / Satellite pages — fund comparison & TER-drag simulation; per-stock performance vs. the core benchmark; linked source documents (factsheets, KIDs, 10-Ks) with ingestion status.
  4. Copilot (right drawer) — per-portfolio chat that answers questions about this portfolio with verifiable citations. Every number in an answer is traced to a SQL result or document chunk; off-topic questions are refused by a guardrail before any expensive model call.

Multiple portfolios are fully isolated — data and chat history — enforced at the database layer (Postgres Row-Level Security), not just in application code.

Why these choices: the demo intentionally exercises the two hardest problems in wealth-tech data engineering — integrating heterogeneous data sources (CSV feeds, market APIs, PDF documents) and hallucination control for LLMs operating over financial databases.

Engineering principles on display
  • Deterministic-first: LLM calls happen in exactly three places (scope guard, planner, synthesiser). Projections, TER drag, risk scores — plain code. The model never computes a number.

4. Data ingestion pipeline

Every new data source — regardless of type — passes the same eight stages. One database (PostgreSQL), two table classes: the router writes market/reference data to shared fact tables (readable by every portfolio), portfolio-owned data to RLS-protected tables, and documents through the RAG branch into pgvector (a fact table). Nothing reaches a table without passing a contract and a quality gate.

pipeline logic validation / staging document / RAG branch analytics / audit New source = one adapter class + registry entry; stages 1–8 unchanged. Retrieval side (embed → hybrid search → rerank, §6) reads what this pipeline writes — ingestion and retrieval share the chunk/embedding contract.

Stage summary

#StageGuarantees
1Landing zoneRaw payload kept immutable with checksum — re-ingest is idempotent, full replay possible
2Adapter dispatchType-specific parsing isolated in one ~30-line class per source
3Contract checkNo untyped record passes; schema drift fails loudly, not silently
4QuarantineInvalid records stored with reason + run id; replayable after adapter fix
5Staging + quality gatesBatch-level reconciliation: sums, row counts, freshness before publish
6RouterData class → right table group: fact tables (shared, read-all) vs portfolio tables (RLS-protected) — one PostgreSQL
7Document branchparse → chunk (page provenance) → embed; shares contract with retrieval pipeline
8Lineageingest_runs: who/what/when/how many — surfaced on UI ingestion page

6. LLM agent architecture (LangGraph)

Orchestrator-centric (same shape as the armlab.io clinical-assistant architecture): a guard classifies the question, the orchestrator routes it to the RAG pipeline (embed → hybrid search → rerank) and/or the data query tools, then a synthesiser writes the answer and a validator gates it.

app logic / routing RAG pipeline deterministic data LLM generation monitoring LLM calls in exactly three nodes: scope_guard (tiny model), orchestrator (routing), synthesiser. Retrieval and every number are deterministic. Second validation failure → honest “cannot answer from data”.

Second LLM surface — stock comparison (plain chain, no agent)

Not every LLM feature needs the graph. The stock comparison feature (satellite screening: "compare NVDA vs ASML vs AMD") is a fixed-shape question — so it's one LangChain call: deterministic SQL fetches fundamentals + magic-formula rows → prompt template injects them as a facts table → single LLM call writes the comparison narrative with a pydantic-parsed verdict → cheap check that every output number appears in the input facts. Grounded by construction (input-controlled) rather than by tools. Same llm_audit_log cost accounting.

facts (SQL) → prompt template → 1 LLM call → structured comparison — vs — open question → LangGraph agent (above)

Demo talking point: this evolves the ungrounded compare_stocks from an older project (prompt-stuffing, unvalidated output — kept in git history) into its grounded form. Two integration patterns shown deliberately: single-call chain for fixed-shape questions, agent graph for open-ended ones — choosing the small tool where the small tool suffices.

7. Portfolio isolation — Row-Level Security

One PostgreSQL, two table classes: fact tables (instruments, prices, financials, sentiment, doc_chunks) are shared — readable by every portfolio, no RLS. Portfolio tables carry Row-Level Security — hard isolation:

ALTER TABLE positions     ENABLE ROW LEVEL SECURITY;
ALTER TABLE chat_messages ENABLE ROW LEVEL SECURITY;

CREATE POLICY per_portfolio ON positions
  USING (portfolio_id = current_setting('app.portfolio_id')::int);

-- request middleware, per connection:
SET app.portfolio_id = '1';
  • Chat in Portfolio 1 is invisible to Portfolio 2 — history rows carry portfolio_id, RLS filters them at the database.
  • The agent's run_sql tool runs on the same scoped connection → even a prompt-injected query cannot read another portfolio.
  • Interview line: “entitlement is enforced below the application layer.”
